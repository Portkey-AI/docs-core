MCP Gateway handles authentication at two independent layers. Understanding this separation is key to configuring secure access.

## Two-Layer Architecture

```mermaid
flowchart TB
    Agent[Your Agent / Client]
    Gateway[MCP Gateway]
    Server[MCP Server]

    Agent -- "API Key / OAuth / External IdP" --> Gateway
    Gateway -- "OAuth Auto / Client Credentials / Headers" --> Server
```

| Layer | Who authenticates | Methods |
|-------|------------------|---------|
| **Gateway Auth** | Agent → Prisma AIRS AI Gateway | API Key, AI Gateway OAuth, External IdP |
| **Server Auth** | The AI Gateway → MCP Server | OAuth Auto, Client Credentials, Headers |

These layers are independent. An agent authenticates to the AI Gateway with an API key. The AI Gateway authenticates to Linear with OAuth. The agent never sees Linear's OAuth tokens.

## Gateway Authentication

Agents prove their identity to the AI Gateway before accessing MCP servers.

<Info>
**How it works:** Requests with an API key use API key auth. Requests with a JWT from an external IdP (with JWT validation configured) use JWT validation. Requests with neither trigger the OAuth flow. No configuration needed—just include an API key or don't.
</Info>

### API Key

The simplest method. Create an API key in the AI Gateway and include it in requests.

```json
{
  "headers": {
    "Authorization": "Bearer your_api_key_here"
  }
}
```

API keys are scoped to workspaces. The key determines which MCP servers the request can access.

Create keys in **Settings > API Keys**. The key must have **`mcp invoke`** permissions.

### OAuth 2.1

For browser-based flows where users authenticate interactively. If no API key is provided, the AI Gateway acts as the OAuth provider and initiates the consent flow. After authentication, your app receives a token to use for MCP requests.

This is useful for:
- End-user applications where users log in
- Interactive tools like Claude Desktop or Cursor (when not using API keys)
- User-level attribution without managing API keys

See [OAuth](/aigw/product/mcp-gateway/authentication/oauth) for details.

### External IdP (Bring Your Own Identity)

Use existing identity providers (Okta, Auth0, Azure AD, Cognito). Configure the AI Gateway to validate tokens from your IdP. Users authenticate with existing identity systems—no Strata Cloud Manager account needed.

This is useful when:
- You have an existing IdP and want SSO
- Users who aren't in the AI Gateway need MCP access
- Compliance requires your own identity infrastructure

See [External OAuth](/aigw/product/mcp-gateway/authentication/external-oauth) for setup.

## MCP Server Authentication

The AI Gateway needs credentials to access upstream MCP servers. Configure this when adding a server.

### OAuth Auto

For MCP servers that support OAuth 2.1 with dynamic client registration. The AI Gateway handles the full OAuth flow automatically.

When a user first calls a tool, the AI Gateway initiates OAuth with the MCP server. The user completes consent (e.g., authorizing access to their Linear account). The AI Gateway stores and refreshes tokens automatically.

Each user gets their own OAuth tokens. User A's Linear access is separate from User B's.

Customize the OAuth client metadata the AI Gateway uses during registration. See [OAuth Client Metadata](/aigw/product/mcp-gateway/authentication/oauth-client-metadata).

### Client Credentials

For MCP servers using OAuth client credentials grant. You provide a client ID and secret when adding the server. The AI Gateway fetches tokens and handles refresh.

All users share the same credentials to the MCP server. Use this for shared resources, not personal data.

### Custom Headers

For MCP servers using API keys or static tokens. Add headers when configuring the server.

```json
{
  "headers": {
    "Authorization": "Bearer api_key_xxx",
    "X-API-Key": "your_key"
  }
}
```

The AI Gateway includes these headers with every request. All users share the same credentials.

See [Custom Auth](/aigw/product/mcp-gateway/authentication/custom-auth) for details.

## Data Flow: Headers and Identity

Beyond authentication, the AI Gateway supports passing contextual information to MCP servers:

### Identity Forwarding

After authenticating a user, the AI Gateway can forward their identity claims to MCP servers. MCP servers can then make authorization decisions without implementing OAuth themselves.

Three methods:
- **Claims Header**: JSON object with user claims
- **Bearer Passthrough**: Forward the original token
- **Signed JWT**: gateway-signed JWT with claims (cryptographically verifiable)

See [Identity Forwarding](/aigw/product/mcp-gateway/authentication/identity-forwarding).

### Header Forwarding

Forward headers from agent requests to MCP servers for distributed tracing, tenant context, or custom metadata.

```json
{
  "forward_headers": ["x-request-id", "x-trace-id", "x-tenant-id"]
}
```

See [Forwarding Headers](/aigw/product/mcp-gateway/authentication/forwarding-headers).

## Choosing the Right Method

| Scenario | Gateway Auth | MCP Server Auth |
|----------|--------------|-----------------|
| Internal developers using the AI Gateway | API Key | OAuth Auto (per-user) |
| End customers with your IdP | External OAuth | OAuth Auto (per-user) |
| Service-to-service access | API Key | Client Credentials or Headers |
| Shared read-only resources | API Key | Custom Headers |

**Use per-user OAuth** when the MCP server accesses user-specific data (email, repos, messages). Each user authorizes their own access.

**Use shared credentials** when the MCP server provides shared resources (knowledge bases, analytics). All users see the same data.

## Credential Isolation

Credentials never cross boundaries.

```
Agent knows:      Portkey API key
Portkey knows:    MCP server OAuth tokens, API keys, user identity claims
MCP Server knows: Its own credentials
```

Agents can't see MCP server credentials. Compromised agent tokens don't expose upstream access. Rotate MCP server credentials without updating agents.
