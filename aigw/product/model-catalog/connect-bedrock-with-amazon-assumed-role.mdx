## Select AWS Assumed Role Authentication

Create a new integration on the AI Gateway, select **Bedrock** as the provider and **AWS Assumed Role** as the authentication method.

## Create an AWS Role for the AI Gateway to Assume
This role you create will be used by the AI Gateway to execute InvokeModel commands on Bedrock models in your AWS account. The setup process will establish a minimal-permission ("least privilege") role and set it up to allow the AI Gateway to assume this role.

### Create a permission policy in your AWS account using the following JSON

These actions cover standard inference — chat completions, the Messages API, embeddings, image generation, and token counting:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockConsole",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:CountTokens"
        ],
      "Resource": "*"
    }
  ]
}
```

<Note>
`bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` also authorize the Converse and ConverseStream APIs, which the AI Gateway uses for most models.

`bedrock:CountTokens` backs the `/v1/messages/count_tokens` endpoint. Clients such as Claude Code call it on every turn, so omitting it shows up as `is not authorized to perform: bedrock:CountTokens`. It is a recent addition to Bedrock — roles created before it existed need it added explicitly.
</Note>

### Additional permissions by feature

Add these only if you use the corresponding feature — everything else works with the three actions above.

| Feature | Additional actions |
| :-- | :-- |
| [Inference profiles](/aigw/integrations/llms/bedrock/aws-bedrock#inference-profiles) (the model ID is an inference profile ARN) | `bedrock:GetInferenceProfile` |
| Model discovery (listing Bedrock models through the AI Gateway) | `bedrock:ListFoundationModels` |
| [Bedrock Guardrails](/aigw/integrations/guardrails/bedrock-guardrails) | `bedrock:ApplyGuardrail` |
| [Reranking](/aigw/integrations/llms/bedrock/rerank) | `bedrock:Rerank` |
| [Batch inference](/aigw/integrations/llms/bedrock/batches) | `bedrock:CreateModelInvocationJob`, `bedrock:GetModelInvocationJob`, `bedrock:ListModelInvocationJobs`, `bedrock:StopModelInvocationJob`, plus S3 access to the input/output bucket and `iam:PassRole` for the Bedrock service role — see the [full batch policy](/aigw/integrations/llms/bedrock/batches#information-about-permissions-and-iam-roles) |
| [Fine-tuning](/aigw/integrations/llms/bedrock/fine-tuning) | `bedrock:CreateModelCustomizationJob`, `bedrock:GetModelCustomizationJob`, `bedrock:ListModelCustomizationJobs`, `bedrock:StopModelCustomizationJob`, plus S3 access to the training-data bucket and `iam:PassRole` |
| [Files](/aigw/integrations/llms/bedrock/files) | `s3:PutObject`, `s3:GetObject`, `s3:GetObjectAttributes`, `s3:AbortMultipartUpload`, `s3:ListBucket` on your bucket |

### Create a new IAM role
Choose *AWS account* as the trusted entity type. If you set an external ID be sure to copy it, we will need it later.

### Add the above policy to the role
Search for the policy you created above and add it to the role.

### Configure Trust Relationship for the role
Once the role is created, open the role and navigate to the *Trust relationships* tab and click *Edit trust policy*.
This is where you will add the AI Gateway AWS account as a trusted entity.

```sh AI Gateway Account ARN
arn:aws:iam::039293892788:role/AirsGwEnterpriseRole
```

<Note>
The above ARN applies to the SaaS deployment of the AI Gateway, managed through [Strata Cloud Manager](https://stratacloudmanager.paloaltonetworks.com/).<br />

To enable **Assumed Role for AWS in your hybrid deployment**, you can refer to [this guide](https://github.com/Portkey-AI/helm/blob/main/charts/portkey-gateway/docs/Bedrock.md).
</Note>

Paste the following JSON into the trust policy editor and click *Update Trust Policy*.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::039293892788:role/AirsGwEnterpriseRole"
      },
      "Action": "sts:AssumeRole",
      "Condition": {}
}
]
}
```

If you set an external ID, add it to the condition as shown below.

```json
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "AWS": "<AI Gateway Account ARN>"
        },
        "Action": "sts:AssumeRole",
        "Condition": {
          "StringEquals": {
            "sts:ExternalId": "<your external ID>"
          }
        }
      }
    ]
}
```

## Configure the integration with the role ARN
Once the role is created, copy the role ARN and paste it into the Bedrock integrations modal in the AI Gateway along with the external ID if you set one and the AWS region you are using.

 You're all set! You can now use the new provider to invoke Bedrock models.

## Attribute Cost and Usage with Session Tags

You can attribute Bedrock cost and audit trails to individual applications, teams, or environments while sharing a single assumed role. Any metadata you send on a request is forwarded to AWS as [STS session tags](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_session-tags.html), so you can segregate spend in AWS Cost Explorer and CloudTrail without provisioning a separate IAM role per application.

<Note>
This feature requires the `AWS_BEDROCK_STS_SESSION_TAGS_ENABLED` environment variable to be set to `true` on the gateway container.
</Note>

Pass the tags using the `metadata` field (or the `x-portkey-metadata` header):

```sh
curl https://aigw.portkey.ai/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $PORTKEY_API_KEY" \
  -H "x-portkey-provider: $PROVIDER_SLUG" \
  -H 'x-portkey-metadata: {"app": "chatbot", "team": "platform", "env": "prod"}' \
  -d '{ "model": "anthropic.claude-3-5-sonnet-20240620-v1:0", "messages": [{"role": "user", "content": "Hello"}] }'
```

<Note>
For AWS to accept session tags, add the `sts:TagSession` action to the trust policy of the role the AI Gateway assumes, alongside the existing `sts:AssumeRole` action.
</Note>
