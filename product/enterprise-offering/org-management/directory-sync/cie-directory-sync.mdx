# CIE Directory Sync

CIE (Cloud Identity Engine) Directory Sync allows you to pull users and groups from your organization's identity provider directories — such as **Entra ID (Azure AD)**, **Okta**, or **On-Premises Active Directory** — into Portkey via Palo Alto's Cloud Identity Engine. Once synced, you can map CIE groups to Portkey workspaces so that users are **automatically provisioned** into the correct workspaces.

---

## Overview

CIE Directory Sync is available for organizations running in **SCM (Strata Cloud Manager) mode**. It replaces the need for manual user provisioning or standalone SCIM integration by leveraging CIE as the centralized identity source.

### How It Works

1. **CIE aggregates directories** — Your organization's identity providers (Entra ID, Okta, on-prem AD) are connected to CIE via the Strata Cloud Manager. CIE syncs and caches user/group data from these directories.
2. **SCM pulls from CIE** — SCM connects to CIE using mTLS and pulls available directories (domains), groups, and group memberships.
3. **Admin maps groups to workspaces** — An admin selects which CIE directory to connect, then maps CIE groups to Portkey workspaces.
4. **Users are auto-provisioned** — Background sync periodically pulls group membership changes from CIE and provisions/deprovisions users in the mapped workspaces automatically.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Domain (Connected Directory)** | An identity provider directory synced into CIE (e.g., `ayushportkey.onmicrosoft.com`). Each domain represents a separate directory source — Entra ID, Okta, on-prem AD, or a CIE-native directory. |
| **Tenant ID** | The CIE tenant identifier for your organization, auto-provisioned during COB (Cloud Onboarding). You never need to enter this manually. |
| **Group** | A directory group from CIE (e.g., an Entra ID security group). Groups contain users that can be mapped to Portkey workspaces. |
| **Group-Workspace Mapping** | A 1:1 link between a CIE group and a Portkey workspace. All members of the mapped group are automatically provisioned into that workspace. |
| **User Identity Attribute** | The CIE user attribute used as the Portkey email address — either **UPN (User Principal Name)** or **Mail (Primary Email)**. |
| **Auth Profile** | The CAS (Cloud Auth Service) authentication profile used to validate user identity during MCP inbound authentication. |

## Prerequisites

Before configuring CIE Directory Sync in Portkey, ensure the following:

1. **CIE is provisioned for your organization** — Your Strata Cloud Manager tenant must have a Directory Sync instance (`app_id: directory_sync`) in its TSG instances. This is set up during Cloud Onboarding (COB).
2. **At least one directory is connected in CIE** — Navigate to CIE and verify that at least one directory (Entra ID, Okta, or On-Premises) has been added and has a successful sync status.
3. **You have SCM admin access** — Only organization admins can configure Directory Sync in Portkey.

<Info>
CIE Directory Sync is only available for SCM Tenants. It is not available in standalone or airgapped Portkey deployments. For non-SCM deployments, use [SCIM Provisioning](/product/enterprise-offering/org-management/scim/scim) instead.
</Info>

## Setting Up Directories in CIE

Before Portkey can sync from CIE, you need to connect your identity provider directories in CIE. This is done in the **Strata Cloud Manager → Cloud Identity Engine** console.

![CIE Directories listing — showing CIE Directory, Entra ID, and Okta directories with sync status, user/group counts, and last sync times](/images/directory-sync/cie-directories-listing.png)

### Adding a New Directory

1. In the CIE console, navigate to **Directory Sync → Directories**.
2. Click **Add New Directory**.
3. You will see the directory type options:

![CIE "Set Up Directory" page — CIE Directory, On-Premises Directory, and Cloud Directory options](/images/directory-sync/cie-set-up-directory.png)

For Portkey integration, the relevant directory types are:

| Directory Type | Provider | Description |
|---------------|----------|-------------|
| **Cloud Directory** | Entra ID (Azure AD), Okta, Google | Connect a cloud identity provider. This is the most common setup. |
| **On-Premises Directory** | Active Directory | Install a Cloud Identity agent to sync from on-prem AD. |
| **CIE Directory** | CIE-native (`cie_directory`) | Create a local directory managed entirely within CIE. |

4. Follow the CIE setup wizard for your chosen directory type.
5. Once the directory syncs successfully, it will appear in the CIE Directories listing with user and group counts.

<Note>
Portkey can connect to **any** directory type that CIE supports. The "Connected Directory" dropdown in Portkey will show all directories that have been successfully synced in CIE.
</Note>

## Configuring Directory Sync in Portkey

Navigate to **AI Gateway → Admin Settings → Authentication → Directory Sync** in the Portkey console.

![Portkey Directory Sync configuration page — Connected Directory, User Identity Attribute, Auth Profile, Sync State, and Group Mappings](/images/directory-sync/portkey-directory-sync-overview.jpg)

### Step 1: Select a Connected Directory

The **Connected Directory** dropdown shows all available directories from CIE, along with their provider type and entity counts (groups and users).

![Connected Directory dropdown — available domains with provider type and user/group counts](/images/directory-sync/connected-directory-dropdown.png)

Each entry displays:
- **Domain name** — the directory domain (e.g., `ayushportkey.onmicrosoft.com`)
- **Provider type** — `aad` (Entra ID), `okta`, `cie_directory` (CIE-native), `ad` (on-prem)
- **Group and user counts** — number of groups and users in that directory

Select the directory you want to sync from. You can also select **None (Disconnected)** to disconnect.

<Warning>
Currently, only **one directory** can be connected at a time. 
</Warning>

**What happens behind the scenes:**

When you open this page, Portkey calls `GET /directory-sync/domains` which:
1. Looks up your organization's `tenant_id` from COB metadata (the `tsg_instances` entry where `app_id === 'directory_sync'`)
2. Calls CIE's `GET /service/directory/v1/domain/status?tenantId={tenant_id}` API
3. Returns the list of available domains with their provider and entity counts

### Step 2: Choose the User Identity Attribute

The **User Identity Attribute** determines which CIE attribute is used as the user's email address in Portkey.

![User Identity Attribute dropdown — UPN (User Principal Name) and Mail (Primary Email) options](/images/directory-sync/user-identity-attr-dropdown.png)

| Attribute | Description | When to Use |
|-----------|-------------|-------------|
| **UPN (User Principal Name)** | The `userPrincipalName` attribute from the directory (e.g., `john@contoso.com`) | Default choice. Use when UPN matches the user's email. |
| **Mail (Primary Email)** | The `mail` attribute from the directory | Use when UPN differs from email (e.g., UPN is `john@contoso.onmicrosoft.com` but email is `john@contoso.com`) |

<Warning>
If the selected attribute is **missing** for a user in CIE, that user will be **skipped** during sync and logged as rejected. Verify that your chosen attribute is populated for all users in your directory.
</Warning>

<Info>
Changing the User Identity Attribute after initial setup triggers an automatic **full re-sync** to update all user email addresses. This is safe — no users are removed during this re-sync.
</Info>

### Step 3: Select an Auth Profile

The **Auth Profile** dropdown shows CAS (Cloud Auth Service) authentication profiles available for your tenant. This profile is used to validate user identity during MCP inbound authentication flows.

### Step 4: Save Configuration

Click **Save** to persist your Connected Directory and User Identity Attribute selections. This calls `PUT /directory-sync/` with:

```json
{
  "domains": ["ayushportkey.onmicrosoft.com"],
  "user_identity_attr": "User Principal Name"
}
```

Once saved, the sync configuration becomes **active** and the background sync scheduler begins monitoring for changes.

## Directory Sync State

The **Directory Sync State** section shows the current health of the sync process.

![Directory Sync State — Status: Success, Last Updated: Sep 4, 2026, Objects Synced: 12 users · 1 groups](/images/directory-sync/sync-state-success.jpg)

| Field | Description |
|-------|-------------|
| **Status** | Current sync status — `Success`, `In Progress`, `Failed`, or `Pending` |
| **Last Updated** | Timestamp of the last successful sync run |
| **Objects Synced** | Count of synced users and groups currently active |

### Full Sync Button

Click the **Full Sync** button to trigger an immediate full membership sync. This is useful when:
- You've just added new group mappings and want to provision users immediately
- You suspect sync drift and want to force a reconciliation
- CIE has been rebuilt (periodic cache refresh) and you want to pick up changes immediately

The full sync button calls `POST /directory-sync/force-sync`, which:
1. Sets `force_full_sync = true` on all domain sync status records
2. Enqueues an immediate sync job (skips the normal scheduler interval)
3. The sync processor ignores delta optimization and does a complete membership pull for all mapped groups

<Info>
If a sync is already in progress, the force sync request will not create a duplicate — it will queue behind the running sync and run as a full sync when it's the job's turn.
</Info>

### Configure in CIE Button

The **Configure in CIE** button links directly to your CIE Directory Sync console, where you can manage directories, agents, and certificates.

## Group Mappings

The **Group Mappings** section is where you map CIE groups to Portkey workspaces. Users in a mapped group are automatically provisioned into the corresponding workspace.

![Group Mappings — "Default Directory" mapped to "Engineering_Workspace"](/images/directory-sync/group-mappings.jpg)

### Adding a Mapping

1. Click **Add Mapping**. The **Add Group Mapping** dialog opens:

![Add Group Mapping dialog — select a CIE Group and a Workspace, then click Add](/images/directory-sync/add-group-mapping-dialog.png)

2. Select a **CIE Group** from the dropdown. The dropdown lists all groups from your connected directory, fetched from CIE's `/cache/group` endpoint. Groups are searchable and paginated.
3. Select a **Portkey Workspace** to map the group to.
4. Click **Add**.

**What happens when you create a mapping:**

1. The group is stored in Portkey's `cie_groups` table (if not already present)
2. The mapping is created in `cie_group_workspace_map`
3. An **immediate full membership sync** is triggered for that specific group — users are provisioned right away, no need to wait for the next background cycle
4. CIE group members are looked up by `cie_unique_identifier` or created as new Portkey users if they don't exist
5. Users are added to the organization and the mapped workspace with the `member` role

### Mapping Rules

- **1:1 mapping** — Each group can only be mapped to one workspace, and each workspace can only have one group mapped to it (enforced in the UI; the backend schema supports M:N for future flexibility)
- **Workspace must exist** — The target workspace must already exist in Portkey. Directory Sync does not create workspaces.
- **Auto-mapping** — If you configure a `workspace_prefix` in settings (e.g., `ws-`), groups matching the pattern `ws-{WorkspaceName}` will be automatically mapped to existing workspaces with that name during group discovery

### Removing a Mapping

Click the **delete** (trash) icon next to a mapping to remove it. This:

1. Archives the group-workspace mapping
2. **Immediately removes** CIE-synced users from that workspace (users provisioned by this mapping only)
3. Performs a **cross-group check** — if a user belongs to another CIE group that is also mapped to the same workspace, that user **retains** workspace access
4. Cleans up the group-user membership tracking records
5. Revokes any OAuth tokens for removed users in that workspace

<Warning>
Deleting a mapping immediately removes users from the workspace. This action cannot be undone — you would need to re-create the mapping and wait for a sync to re-provision users.
</Warning>

## How Background Sync Works

Once configured, Directory Sync runs automatically in the background.

### Sync Architecture

```
┌────────────────────────┐     ┌─────────────────────────────────┐
│  Fanout Scheduler      │     │  Per-Org Sync Processor         │
│  (runs every 1 minute) │     │                                 │
│                        │     │  1. Load config + tenant_id     │
│  For each active org:  │     │  2. Get mapped groups           │
│  - Check if sync due   │────►│  3. Check CIE incrsyncstatus    │
│  - Check force_full    │     │  4. Full or Delta sync          │
│  - Enqueue sync job    │     │  5. Provision/remove users      │
│                        │     │  6. Update sync cursors         │
└────────────────────────┘     └─────────────────────────────────┘
```

### Sync Interval

The background sync runs on a configurable interval (default: **15 minutes**, controlled by the `CIE_SYNC_INTERVAL_SECONDS` environment variable). The fanout scheduler checks every minute whether any organization is due for a sync.

### Sync Strategy: Full vs Delta

Each sync cycle uses one of three strategies, determined by CIE's incremental sync status API:

| CIE Response | Strategy | Description |
|-------------|----------|-------------|
| **HTTP 281** | **Skip** | No changes since last sync — nothing to do |
| **HTTP 200** | **Delta** | Changes available — only fetch and process what changed |
| **HTTP 280** | **Full** | Full resync required — CIE rebuilt its cache or delta cursor expired |

**Delta sync optimization:** When delta is available, Portkey first calls CIE's `fetchChangedMembershipGroups` endpoint to find which groups had membership changes. Only those groups are synced — if you have 50 mapped groups but only 2 changed, only 2 API calls are made.

### What Happens During a Sync

**For new members (users joining a group):**
1. User is matched by `cie_unique_identifier` in Portkey's user table
2. If no match — a new Portkey user is created with the name from CIE's `Common-Name` attribute and email from the admin-selected attribute (UPN or Mail)
3. User is added to the organization and the mapped workspace with `member` role
4. API keys are auto-created for the workspace

**For removed members (users leaving a group):**
1. A **cross-group check** is performed — if the user belongs to another CIE group also mapped to the same workspace, they keep access
2. If the user has no other group granting workspace access, they are removed from the workspace
3. OAuth tokens for the removed user in that workspace are revoked

**For existing members:**
1. User attributes (name, email) are refreshed from CIE data
2. Workspace membership is ensured (idempotent — no duplicate entries)

### Sync Observability

The sync processor emits OpenTelemetry metrics:

| Metric | Description |
|--------|-------------|
| `cie_sync_duration_seconds` | Duration of each sync run (with `status` and `strategy` labels) |
| `cie_sync_runs_total` | Counter of sync runs (success/failed) |
| `cie_sync_users_total` | Users provisioned, updated, or removed |
| `cie_sync_api_calls_total` | CIE API calls made (with endpoint and status labels) |

## Disabling Directory Sync

To disable Directory Sync entirely:

1. Navigate to **Admin Settings → Authentication → Directory Sync**
2. Select **None (Disconnected)** from the Connected Directory dropdown, or call `DELETE /directory-sync/`

**What happens when you disable sync:**

1. All CIE-synced users are **removed from their mapped workspaces** (with cross-group safety checks)
2. All group-workspace mappings are archived
3. All group and sync status records are archived
4. The sync configuration is set to `archived`

<Warning>
Disabling Directory Sync immediately removes all CIE-provisioned users from their workspaces. This is a destructive action. Users can be re-provisioned by re-enabling sync and re-creating group mappings.
</Warning>

To **re-enable** sync after disabling:
1. Select a Connected Directory again and save
2. Group mappings do **not** carry over — you must re-create them explicitly
3. A full sync will run to provision users into the newly mapped workspaces

## API Reference

All Directory Sync APIs are served under `/ai_gw/admin/v2/directory-sync/` and require SCM admin authentication.

### Get Configuration

```
GET /directory-sync/
```

Returns the current sync configuration.

**Response:**
```json
{
  "status": "active",
  "tenant_id": "1128814283722418816",
  "region": "us",
  "domains": ["ayushportkey.onmicrosoft.com"],
  "user_identity_attr": "User Principal Name",
  "settings": {}
}
```

### Update Configuration

```
PUT /directory-sync/
```

Enable or update sync configuration.

**Request:**
```json
{
  "domains": ["ayushportkey.onmicrosoft.com"],
  "user_identity_attr": "User Principal Name"
}
```

**Validation:**
- `domains` must be an array with exactly 1 entry (multi-domain not yet supported)
- `user_identity_attr` must be `"User Principal Name"` or `"Mail"`

### Delete Configuration

```
DELETE /directory-sync/
```

Disable sync and archive all data. Optionally accepts a `domain` in the request body.

### List Available Domains

```
GET /directory-sync/domains
```

Returns all directories available in CIE for this organization.

**Response:**
```json
{
  "domains": [
    {
      "domain": "ayushportkey.onmicrosoft.com",
      "provider": "aad",
      "count": { "group": 10, "user": 22 }
    },
    {
      "domain": "integrator-6735440.okta.com",
      "provider": "okta",
      "count": { "group": 10, "user": 10 }
    }
  ]
}
```

### List Groups

```
GET /directory-sync/groups?search=&page=1&page_size=50&domain=&refresh=false
```

Returns groups from the connected directory. Results are cached for 5 minutes; pass `refresh=true` to force a fresh CIE call.

### Get Sync Status

```
GET /directory-sync/status
```

Returns per-domain sync health including last sync time, strategy used, success/failure stats, and consecutive failure count.

### Force Full Sync

```
POST /directory-sync/force-sync
```

Triggers an immediate full membership sync for all mapped groups.

### Create Group-Workspace Mapping

```
POST /directory-sync/group-workspace-mappings
```

**Request:**
```json
{
  "group_unique_identifier": "b39bd5e4-4d44-43f6-90d8-ff0f878a38f7",
  "group_name": "Engineering",
  "workspace_id": "ws-engineering-uuid"
}
```

Triggers an immediate membership sync for the newly mapped group.

### List Mappings

```
GET /directory-sync/group-workspace-mappings
```

### Delete Mapping

```
DELETE /directory-sync/group-workspace-mappings/:id
```

Removes users from the workspace and archives the mapping.

## Troubleshooting

### Common Issues

| Issue | Cause | Resolution |
|-------|-------|------------|
| **No domains shown** in Connected Directory dropdown | CIE not provisioned for this org, or no directories added in CIE | Check that your SCM tenant has `directory_sync` in `tsg_instances`. Add directories in CIE. |
| **Users not provisioned** after mapping | Selected User Identity Attribute is missing for those users | Check CIE to confirm users have the UPN or Mail attribute populated. Switch attribute if needed. |
| **Sync status shows "Failed"** | CIE API unreachable, mTLS cert expired, or internal error | Check `cie_sync_duration_seconds` metric. Verify `CIE_TLS_CERT` and `CIE_TLS_KEY` env vars. Try a manual Full Sync. |
| **Users not removed** after deleting mapping | User belongs to another group also mapped to the same workspace | This is by design — cross-group check prevents removing users who have access through another mapping. |
| **Sync shows "Skip" every cycle** | No membership changes detected in CIE | This is normal. CIE returns HTTP 281 when nothing changed. Use the Full Sync button to force a refresh. |
| **Delta sync falling back to full** | CIE cache was rebuilt, or cursor expired | This is expected behavior. CIE periodically rebuilds its cache (returns HTTP 280), which triggers a full resync. This acts as a self-healing mechanism. |

## CIE Directory Sync vs SCIM Provisioning

| Feature | CIE Directory Sync | SCIM Provisioning |
|---------|-------------------|-------------------|
| **Direction** | Pull (Portkey pulls from CIE) | Push (IdP pushes to Portkey) |
| **Identity Source** | CIE (aggregates multiple IdPs) | Direct from IdP (Okta, Azure AD) |
| **Deployment Mode** | SCM only | Any deployment |
| **Group Mapping** | 1 group → 1 workspace (Phase 1) | 1 group → many workspaces |
| **Roles** | All users get `member` role | Configurable per-group (admin, manager, member) |
| **Sync Trigger** | Automatic background + manual Full Sync | Real-time push from IdP |
| **User Creation** | Automatic from CIE data | Automatic from SCIM payload |
| **Authentication** | mTLS (CIE) + CAS (MCP users) | SCIM bearer token |

<Info>
CIE Directory Sync and SCIM Provisioning are **mutually exclusive** — an organization uses one or the other, not both. SCM-mode organizations use CIE; non-SCM organizations use SCIM.
</Info>
